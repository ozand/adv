## Dataflow and interpretation

Concrete outputs in the reviewed records are limited to AP-record display/buffer updates and the separate port-check positive-result output (Marauder `WiFiScan.cpp` cited above); portal-related formatted output to serial, buffer, and optional display (`EvilPortal.cpp` [L124-L141](https://github.com/justcallmekoko/esp32marauder/blob/b2b9f92382eb60b39b8741be3b567e416cdbe672/esp32_marauder/EvilPortal.cpp#L124-L141), [L399-L424](https://github.com/justcallmekoko/esp32marauder/blob/b2b9f92382eb60b39b8741be3b567e416cdbe672/esp32_marauder/EvilPortal.cpp#L399-L424)); Bruce's converted auth-mode label in an “Auth mode” UI row (`ap_info.cpp` [L12-L26](https://github.com/brucedevices/firmware/blob/a59213f3ec6cd302fa32c2042b2700c9c24d991a/src/modules/wifi/ap_info.cpp#L12-L26), [L74-L90](https://github.com/brucedevices/firmware/blob/a59213f3ec6cd302fa32c2042b2700c9c24d991a/src/modules/wifi/ap_info.cpp#L74-L90), [L109-L123](https://github.com/brucedevices/firmware/blob/a59213f3ec6cd302fa32c2042b2700c9c24d991a/src/modules/wifi/ap_info.cpp#L109-L123)); and packet-buffer append structure in the handshake-related callback (`WiFiScan.cpp` [L5128-L5210](https://github.com/justcallmekoko/esp32marauder/blob/b2b9f92382eb60b39b8741be3b567e416cdbe672/esp32_marauder/WiFiScan.cpp#L5128-L5210)). Formats, full schemas, runtime values, destinations beyond those named, and retention are otherwise unknown.

Bruce maps AP-record `authmode` tokens to static labels, including a fallback, then places the result in a UI row. These label strings are not WPA/802.11 protocol semantics, negotiation, authentication, or proof of supported security modes. Reuse the existing [AP authentication-mode label concept](../../concepts/operations/wifi-ap-auth-labels.md); it is distinct from the [passive-monitoring receive-path concept](../../concepts/operations/wifi-passive-monitoring.md), whose shared receive path likewise does not establish zero transmission.

Forward trace: the source records connect selected code structures to receive, record, label, callback, or output steps only. Device identity/component, firmware-to-device relationship, runtime prerequisites/configuration, data formats and complete retention remain unknown. Backward trace from desired data to a verified device/setup also stops at those unknown edges; no prerequisite or compatibility path is inferred. Editorial scenario: a reader compares these source-level patterns and gaps. It is not an observed Cardputer scenario or usage recommendation.

## Protocol and security-generation context

The new [Wi-Fi generation and security context entity](../../entities/protocols/wifi-80211.md) uses two official Wi-Fi Alliance overviews and versioned ESP-IDF v5.2.3 documentation for the ESP32-C6 target. The Alliance overview names Wi-Fi 4/5/6/7 and describes selected features; its Wi-Fi 6 text says 6 GHz was introduced alongside 2.4/5 GHz, without distinguishing Wi-Fi 6E or saying all Wi-Fi 6 devices use 6 GHz. Its public security page summarizes WPA3 and PMF but does not compare WPA2. The versioned SDK page lists 802.11b/g/n/ax and WPA/WPA2/WPA3 families for ESP32-C6. These source-reported statements describe standards/product context and one SDK target; they do not prove support by any cited Cardputer firmware or device.

The pinned [m5porkchop README](https://github.com/0ct0sec/m5porkchop/blob/38d7078c09205e23b65018fd486a5fd1e40ee440/README.md#L131-L134) separately reports an optional M5MonsterC5 coprocessor as dual-band Wi-Fi 6/802.11ax over UART. This is upstream-reported context only, not an inspected integration path or Cardputer compatibility. Likewise the [Bruce AP authentication-label concept](../../concepts/operations/wifi-ap-auth-labels.md) documents enum-token-to-string mapping, not protocol semantics or negotiation evidence.

Remaining gaps include primary IEEE normative text, a WPA2-specific Alliance comparison, SDK evidence for other targets such as the Cardputer's ESP32-S3 or the mentioned ESP32-C5 coprocessor, and inspected application integration. No such support or device behavior is inferred. This bounded batch used the authorized Surf browser for the official pages; no local browser failure is claimed.
