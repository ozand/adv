# DeviceOps — архитектура

**Статус:** Proposed, не реализованный сервис. **Epic:** [#66](https://github.com/ozand/adv/issues/66). Решения о стеке и месте кода: [D01 / #68](https://github.com/ozand/adv/issues/68). Требования: [PRD](PRD.md).

## 1. Слои и ответственность

```text
Local agent / Web chat / Operator / Approved CI job
                         |
                   CLI / MCP / UI
                         |
              DeviceOps application core
     identity + capabilities + policy + plans + jobs
                         |
                 Device session broker
          single writer + lifecycle + evidence
                         |
        +----------------+----------------+
        |                |                |
   Runtime serial    ROM flashing     Network adapter
   diagnostic API    backend          config / OTA
        |                |                |
        +----------------+----------------+
                         |
                       ESP32
```

| Компонент | Ответственность | Чего не делает |
|---|---|---|
| Frontend CLI/MCP | Валидация формата, аутентифицированный контекст, представление результата | Не открывает USB отдельно от broker и не выдаёт grants |
| Capability registry | Профили поддерживаемых firmware/операций и уровень evidence | Не выводит возможности из одного названия чипа |
| Policy/plan engine | Проверка эффектов, target, согласия, версии policy и плана | Не полагается на обещания модели |
| Job store / executor | Сохранение намерений, последовательное исполнение, состояние после сбоя | Не обещает exactly-once аппаратный эффект |
| Session broker | Владение транспортом, handoff, ограничения параллелизма и quarantine | Не предполагает, что expiry lease остановил физический I/O |
| Adapter | Реализация конкретного протокола с bounds и provenance | Не расширяет разрешённые операции |
| Evidence store | Ограниченные результаты и sanitized receipts | Не публикует raw logs/секреты в Git |

Агентный runtime (Pi, Codex или другой клиент) остаётся снаружи. Он планирует разработку и использует инструменты; выполнение критической записи не зависит от непрерывной генерации модели.

## 2. Предлагаемый MVP: один host-процесс

Для первой версии достаточно одного владельца core, локального транзакционного хранилища и нескольких клиентов. SQLite, Python 3.11+, Windows 11-first и package direction предлагаются в [D01](D01-DECISION.md) и ADR-015; это не принятые зависимости/решения до owner review. Отдельный кластер, брокер сообщений и облачная база не нужны для проверки первого сценария.

CLI/MCP фасад обращается к этому владельцу через локальный защищённый IPC или согласованный in-process режим. Запуск второго фасада не должен создавать второго исполнителя одной платы. ОС-специфичные права IPC и exclusive-open serial проходят отдельную квалификацию.

Хранилище содержит devices/bindings, plans, operations/events, grants и минимальные receipts. Секреты — в отдельном доверенном secret provider, а не в таблицах, доступных модели. Реальные locator/USB-данные и DB находятся вне публичного checkout. Для журналов и DB определяются retention, квоты, миграции и backup/restore; восстановление DB не повторяет прошлые команды.

## 3. Путь запроса

1. Frontend получает principal из доверенного канала, не из произвольного JSON-поля агента.
2. Core проверяет schema, capability, target binding и permission; связывает `request_id` с нормализованным запросом.
3. Для изменения core формирует/находит immutable plan. Доверенная сторона выдаёт привязанное разрешение.
4. Операция записывается до dispatch. Broker получает исключительное владение и заново проверяет текущие условия.
5. Adapter исполняет ограниченное действие и сообщает стадии передачи/ответа; core сохраняет события.
6. Postcondition проверяется в пределах capability. Клиент получает `operation_id` и затем читает результат.

Недопустимый запрос отвергается до dispatch. Потерянный ответ после передачи — отдельный случай, не обычный отказ без эффекта. Подробности: [CONTRACTS](CONTRACTS.md).

## 4. Runtime и ROM — разные режимы

Работающий firmware serial API и ROM flashing protocol не обслуживаются одновременно. Для deployment нужен явный переход `runtime -> bootloader -> runtime`: завершить reader, сохранить сессию, проверить право reset/flash, передать транспорт backend, затем повторно установить binding после USB re-enumeration.

Нельзя выбрать первый появившийся COM-порт. Если однозначная связь с прежним target потеряна, операция блокируется до rebinding. USB path, VID/PID и заявленная версия firmware — evidence разной силы, не универсальное доказательство идентичности.

Открытие порта само может менять управляющие линии; read-only `status` на уровне приложения не доказывает отсутствие reset при подключении. Эти эффекты задаёт connection profile и проверяет аппаратный тест.

## 5. Удалённый вебчат

```text
Web chat MCP client
        |
Authenticated gateway or supported outbound tunnel
        |
Local DeviceOps frontend -> the same core -> USB
```

Используется тот же каталог операций и policy. Remote client не получает прямой raw serial socket. Протокол и SDK MCP закрепляются в D06; доступность конкретного tunnel/workspace проверяется в D09. Первичные источники перечислены в [REFERENCES](REFERENCES.md), но настройки пользователя этим документом не проверены.

Первый remote integration test следует проводить с fake device. Публикация endpoint, установка tunnel client и включение account permissions — отдельные разрешаемые действия. Подключение вебчата не выдаёт право прошивки.

## 6. Необязательный браузерный исполнитель

```text
Web chat -> session gateway <- browser support page -> Web Serial -> ESP32
```

Страница получает пользовательское разрешение, связывается с аутентифицированной сессией и исполняет только именованные операции. Сервер, browser executor и core сохраняют одинаковые effect semantics; время жизни страницы и USB-сессии отражается в результатах. Закрытие или заморозка вкладки не даёт оснований повторить неопределённое действие на другом исполнителе.

ESP Web Tools размещается как отдельный операторский установщик. Его manifest может генерироваться из общего каталога. Обычный EWT-компонент сам не обеспечивает DeviceOps grants, подписи, board identity или transactional execution. Агентный браузерный flash требует отдельного адаптера и тех же gates; автоматизация кнопок установщика не заменяет контракт.

Встроенный iframe вебчата и WebMCP не являются обязательными предпосылками. Поддержка USB/permissions проверяется в конкретном host/browser, иначе используется отдельная страница.

## 7. Сетевая прошивка и OTA

Сетевая диагностика/config/OTA возможны лишь для firmware, который предоставляет соответствующий API. Можно подключать как компактный protocol через host gateway, так и проверенный device-side MCP. Выбор зависит от конкретного профиля и не заставляет все ESP32 содержать MCP runtime.

Сервис в самой прошивке не является независимым recovery-каналом при её неуспешном запуске. Поэтому сетевой путь не отменяет отдельно проверенный USB/ROM recovery. См. [DEPLOYMENT](DEPLOYMENT.md).

## 8. Расширяемость и границы кода

Adapter interface должен получать bounded request, immutable target/plan context, отмену с явной семантикой и sink структурированных событий. Возвращаются подтверждённые стадии и неопределённость, не только Boolean success. Плагины не загружаются из произвольного URL агента: registry разрешённых адаптеров и версии контролируются оператором.

В `adv` размещаются документы, координация и reviewed знания. Предпочтительное место runtime — отдельный согласованный репозиторий; конкретный адрес пока не выбран. Существующий [host CLI](../../scripts/adv_diagnostic_cli.py) — кандидат для reuse валидаторов, не готовый DeviceOps daemon. Не переносить его или сторонний код без проверки границ и лицензий.

## 9. Решения D01

Предлагаемый выбор host language/OS/IPC/storage и место реализации описаны в [D01](D01-DECISION.md) и Proposed ADR-015; все требуют owner review. Закреплённые версии SDK, достаточная identity для каждого risk tier, формат grant/plan integrity и процедура hardware допуска остаются открытыми для соответствующих D02/D03 и квалификационных работ. Браузер и provider-specific tunnel не должны становиться обязательными зависимостями core.
