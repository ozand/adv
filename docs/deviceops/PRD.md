# DeviceOps — требования к сервису

**Статус:** проект требований для review. **Дата:** 2026-10-12. **Epic:** [#66](https://github.com/ozand/adv/issues/66). Общие границы и навигация: [README](README.md).

## 1. Проблема и цель

Сегодня операции разработки, диагностики и прошивки могут выполняться разными инструментами с разными представлениями о результате. Агенту недостаточно получить текст «успешно»: необходимо знать, к какой плате и прошивке относилось действие, что было разрешено, дошла ли команда до устройства и какой результат действительно наблюдался.

Цель — один семантический слой DeviceOps, который связывает существующие инструменты с проверяемыми заданиями. Он не должен становиться новой LLM-платформой или переписывать SDK, ROM-загрузчик и тестовые фреймворки.

## 2. Пользователи и сценарии

| Пользователь | Запрос | Ожидаемый результат |
|---|---|---|
| Локальный coding agent | Проверить симптом на выбранной плате | Ограниченная диагностика, evidence и гипотезы отдельно |
| Агент из вебчата | Получить статус подключённого устройства | Тот же результат через защищённый MCP, без угадывания локального порта |
| Оператор | Разрешить конкретное обновление | Понятный план эффектов, подтверждение и проверка запуска |
| Разработчик / CI | Проверить новую сборку на стенде | Артефакт точной ревизии, ограниченный тест и воспроизводимый receipt |
| Пользователь поддержки | Подключить устройство на одну сессию | Необязательная браузерная страница с видимыми операциями и отзывом доступа |

Сервис должен допускать несколько проектов и профилей плат. Наличие одного семейства чипов не устанавливает совместимость периферии, разметки или firmware API.

## 3. Объём по этапам

**MVP-A, без оборудования:** core с долговечными заданиями, policy, fake transport, один профиль текущей диагностики ADV, CLI и локальный MCP, детерминированные проверки. Нет скрытого реального I/O при запуске тестов или перечислении инструментов.

**MVP-B, отдельно допущенная плата:** минимальное подключение и `status`, корректный отчёт и явная потеря сессии. Если нужная прошивка не установлена, результат — блокировка с причиной; установка не становится неявным шагом диагностики.

**Следующий вертикальный сценарий:** идентичная диагностика из выбранного вебчата. Затем каталог артефактов и безопасное планирование; только после проверок — исполнение deployment.

**Расширения:** настройка поддерживаемой прошивки, OTA, браузерный мост, дополнительные платы и тесты. Их отсутствие не блокирует локальный MVP. Полноценное управление парком и автоматические массовые обновления вне первого этапа.

## 4. Проверяемые требования

| ID | Требование | Проверка / владелец |
|---|---|---|
| R01 | CLI и MCP вызывают общий core, с одинаковыми результатами и запретами | V01; D06 |
| R02 | Устройство, транспортная сессия и известная прошивка различаются; неопределённая identity не маскируется | V02–V03; D02/D03/D05 |
| R03 | Каждая операция объявляет входы, выходы, эффекты, полномочия, пределы и retry/cancel semantics | V04; D02 |
| R04 | Проверка полномочий происходит до I/O и повторно перед запуском из очереди | V05–V06; D03 |
| R05 | В управляемой сессии один исполнитель владеет устройством; lease expiry не создаёт второго writer | V07; D04 |
| R06 | Задания и evidence переживают сбой процесса; сомнительное исполнение не повторяется автоматически | V08–V10; D04 |
| R07 | Существующие ADR-006/009 сохраняются; нет автоматического SD/audio/run/reset | V11–V12; D05 |

| R11 | Очереди, сообщения, журналы, сроки хранения и ожидания ограничены; перегрузка даёт явный результат | V04/V19; D02/D04 |

## 5. Критерии успеха

Для MVP-A все обязательные fake conformance cases должны завершиться с ожидаемым результатом; пропущенный тест не считается пройденным. Счётчик реальных device/network calls в offline suite равен нулю. Паритет CLI/MCP проверяется на success, deny, busy, malformed input и неизвестном исходе, а не только на happy path.

После crash/restart возвращается прежний `operation_id`; отсутствие ACK не приводит ко второй отправке mutating команды. При смене target/артефакта старый grant непригоден. В каждом отчёте видны источник, версия, ограничения и непроверенные свойства.

Численные требования к latency, throughput и памяти нельзя объявить достигнутыми без измерения. D02 фиксирует конечные ресурсные пределы; D14 измеряет фактические показатели выбранной конфигурации. Производительность не служит причиной убрать проверки полномочий или подавить неопределённость.

## 6. Non-goals и предположения

Не входят: произвольная serial/shell/GPIO-консоль для модели; чтение всего хранилища; автоматическая прошивка любого ESP32; eFuse/key provisioning; полноценный удалённый рабочий стол; обязательный MCP на микроконтроллере; гарантированная совместимость всех браузеров/вебчатов.

Предполагается доверенный оператор и контролируемый host. Сервис не защищает устройство от владельца с полным доступом к ОС и USB в обход broker. Для production такая граница должна быть принята явно.

Устройство не обязано иметь сеть. Авторизация USB-доступа и поддержка конкретных firmware-команд — предварительные условия, не следствия установки Skill.

## 7. Принятие и изменения

Направление подтверждено владельцем; подробный PRD и ADR предлагаются к review в D01. Изменение публичных схем, эффектов или trust boundary проходит отдельный ADR и обновление связанных тестов. Мердж документации не является аппаратным допуском и не подтверждает все будущие implementation choices.
