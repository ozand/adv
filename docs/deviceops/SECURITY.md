# DeviceOps — безопасность и полномочия

**Статус:** проект threat model и требований enforcement. **Задача:** [D03 / #70](https://github.com/ozand/adv/issues/70). **Epic:** [#66](https://github.com/ozand/adv/issues/66). Не является заключением security audit или уже принятой схемой аутентификации.

## 1. Что защищаем

Целевые активы: правильное устройство, его прошивка/настройки/данные, секреты, доступность стенда, целостность артефактов и достоверность результатов. Модель, тексты логов, имена Wi-Fi-сетей, сторонние firmware и непроверенные PR не считаются доверенными источниками разрешений.

Доверенные роли: оператор, issuer разрешений, проверенный DeviceOps core и контролируемый executor. Администратор ОС и физический владелец USB могут обойти сервис; его policy не следует представлять как защиту от такого противника. Ограничения OS-пользователя, IPC/serial permissions и размещения секретов — часть выбранной конфигурации, проверяемая отдельно.

## 2. Границы доверия

| Граница | Риск | Требование |
|---|---|---|
| Агент → frontend | Подмена principal, аргументов, самоодобрение | Principal из authenticated context; schemas/limits; никакого `approved=true` как доказательства |
| Frontend → core | Обход policy через отдельный CLI/backend | Все эффекты проходят один engine и broker |
| Core → executor/USB | Не та плата, второй writer, stale worker | Target/session binding, exclusive ownership, fencing и quarantine |
| Artifact store → flasher | Подмена файла, traversal, неверный layout | Immutable digest, trust policy, проверка диапазонов и TOCTOU |
| Непроверенный код → CI/стенд | Кража ключей, произвольный доступ к USB | Build sandbox отдельно от доверенного hardware runner |
| Устройство → агент | Prompt injection, утечка, malformed/огромный ответ | Bounded parser, redaction, фиксированные result schemas; текст только данные |
| Вебчат/браузер → gateway | Cross-user access, replay, origin confusion | Auth, target-bound session, expiry/revoke, проверка Origin/Host где применимо |

## 3. Модель разрешений

Предлагаемые режимы: observe, diagnostic, lab-deploy и managed-deploy. Они раскрываются в конкретные именованные операции, эффекты и профили, а не в универсальный уровень «доверяем агенту».

Grant содержит issuer/principal, target binding и допустимую силу identity, operation с нормализованными аргументами либо plan digest, artifact digest при deployment, policy revision, expiry, max uses/budget и разрешённые эффекты. Секрет самого grant не включается в публичный receipt. Проверяются подлинность/наличие доверенной записи, scope, актуальность, отзыв и расход бюджета. Конкретный механизм подписи или хранения принимает D03.

Проверка обязательна при принятии и непосредственно перед запуском из очереди. Изменение target, bytes, layout, адаптера или существенных предусловий требует нового plan/grant. Agent-supplied labels, MCP annotations и текст Skill могут описывать риск, но не выдавать полномочия.

Оператор может заранее разрешить bounded диагностику на выделенной плате или ограниченное число прошивок конкретного стендового профиля. Это позволяет автоматизацию без подтверждения каждой строки serial. Разрешение не распространяется на соседнюю плату, неизвестный артефакт, произвольный SD/audio тест или необратимую операцию.

## 4. Identity и single writer

VID/PID, OS locator, выбранный порт, серийный номер и firmware marker имеют разную доказательную силу. Уровень `operator_bound` допустим лишь там, где policy принимает ручную привязку. Он не должен называться криптографической аттестацией. После re-enumeration неоднозначность блокирует mutating I/O.

Один broker обслуживает чтение и запись; клиентам выдаются копии разрешённых результатов. Истечение lease или потеря heartbeat не доказывают, что старый worker перестал писать. Нельзя передать ownership до подтверждённого завершения/остановки или безопасной изоляции прежнего исполнителя. На fake backend тестируются competing clients, stale generation и worker, продолжающий I/O после expiry.

Браузерная вкладка — отдельный executor с ограниченным временем жизни. Сервер не может одной записью в DB гарантировать прекращение её USB-действий. Поэтому сначала реализуется read-oriented поддержка; агентный browser flash требует отдельной квалификации.

## 5. Секреты, журналы и конфиденциальность

Агент использует только разрешённую opaque secret reference. Значение разрешает доверенный компонент непосредственно перед применением; identifier сам не позволяет читать произвольный secret. Отчёт показывает имя профиля/факт применения, не пароль или токен. Не помещать секреты в argv, URL, stdout, исключения, firmware manifests или public issues.

Raw logs и memory/flash dumps не являются обычным результатом диагностики. Для допустимого источника логов задаются fields/редакция, размер, возраст, доступ и retention; экспорт проходит отдельную privacy-проверку. Публичный `adv` хранит только sanitized выводы и ссылки на проверенные исходники. Hash чувствительных данных тоже не всегда безопасен: не публиковать низкоэнтропийные секреты даже в виде digest.

## 6. Supply chain и исполнение

Загрузка из URL не равна доверию издателю. SHA-256 проверяет соответствие выбранным bytes, а подпись/одобрение источника — отдельная policy. Разрешены только закреплённые backend binaries и аргументы без shell interpolation. Не загружать произвольные плагины и не выполнять скрипты из манифеста.

Build job работает без USB и эксплуатационных credentials. Hardware runner принимает разрешённый артефакт и ограниченный test manifest, а не произвольный shell job из PR. Автор изменения не должен одновременно ослабить acceptance test и выдать это за устранение дефекта без отдельного review.

## 7. Отзыв, остановка и остаточные риски

Revoke запрещает новые действия и запуск из очереди. Для уже начатого эффекта применяется заранее определённая безопасная политика: остановка в safe point либо завершение критической стадии. Нельзя сообщать «отменено и ничего не изменилось», если это неизвестно. Дальнейшее восстановление может требовать отдельного разрешения.

Гарантии hardware identity, безопасного reset, сохранения flash-данных и recovery зависят от конкретной платы/bootloader/firmware. Даже успешная верификация образа не доказывает его безопасность или правильность физических выходов. eFuse, ключи secure boot и необратимые изменения не предоставляются общим агентным API.

## 8. Security gate

Перед реальным I/O требуется review exact code/config SHA, negative fixtures V02–V10/V13–V20 из [VALIDATION](VALIDATION.md), документированный target/connection profile и отдельный runtime допуск. Для конкретного operation/profile обязательны все применимые negative fixtures из [VALIDATION](VALIDATION.md), проверенные до включения соответствующего эффекта. Минимальный G3 `connect/status` профиль требует проверки применимых connection/identity/authorization и single-writer controls (включая V02–V07 и V11), но не требует deployment, secret, remote или browser fixtures, пока эти эффекты не включены. V13–V20 и другие группы остаются обязательными до разрешения соответствующих deployment/secret/remote/browser/queue effects; отсутствие тестов на необязательную возможность не является разрешением включить её. Перед remote exposure дополнительно проверяются клиентская auth-модель, scopes, replay, rate limits и revocation. Ни один интерфейс не получает автоматически больше прав только потому, что он локальный или использует MCP.
