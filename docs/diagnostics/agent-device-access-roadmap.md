# Дорожная карта доступа LLM-агента к Cardputer

**Статус:** исследовательский план; направление реализации не выбрано
**Issue:** [#33](https://github.com/ozand/adv/issues/33)
**Связанный контракт:** [ADR-006](../adr/ADR-006-hardware-diagnostic-serial-json.md)

## Цель оператора

Дать LLM-агенту возможность подключаться к Cardputer и использовать максимально полный набор реально доступных и безопасно управляемых функций: сведения о ПО и прошивке, диагностические данные, аппаратные модули и ресурсы. Цель — полезный и проверяемый доступ к возможностям устройства, а не конкретный транспорт или протокол. «Максимально полный» не означает неограниченный: каждая операция должна иметь описанные эффекты, полномочия, ограничения и способ проверки.

Документ сравнивает два направления — адаптер на хосте (CLI/MCP) и сетевой MCP-сервис на устройстве. Ни одно не выбрано и не разрешено к реализации. Возможна также поэтапная или гибридная схема; это вопрос будущего проектирования.

## Что известно сейчас

В репозитории есть compile-only диагностическая прошивка и ограниченный host CLI. Принятый ADR-006 описывает фиксированные команды `status`, `sd_test`, `run <ID>`, `result <ID>`: ограниченный результат `run` хранится в RAM, запрос результата read-only, SD отдельно opt-in, физические проверки не объявляются PASS без наблюдения. Это узкий диагностический интерфейс, не универсальное управление устройством.

Документированный источник и сборка не доказывают работу на реальном устройстве. Не следует считать проверенными доступность USB/COM, успешность конкретной команды, состояние периферии, безопасность новых операций, совместимость установленной прошивки или возможность сетевого доступа. Перед любым опытом с устройством нужны отдельное разрешение, проверка точной команды и условий остановки; установка/прошивка требует отдельного разрешения и плана восстановления.

## Направления для оценки

| Критерий | Host-side CLI/MCP адаптер | Device-side MCP/network |
|---|---|---|
| Где исполняется агентский интерфейс | На доверенном компьютере; связывает MCP/CLI с ограниченным локальным API устройства | В прошивке/сервисе устройства; агент обращается к сетевому endpoint |
| Возможный охват | Может объединять документированные команды устройства и доступные host-инструменты; не добавляет отсутствующие аппаратные функции | Потенциально доступен без постоянно подключённого host; ограничен тем, что экспонирует прошивка |
| Доступность | Требует работающего host, драйвера/транспорта и локального процесса | Требует сети, сервиса и совместимой прошивки; фактическая доступность не подтверждена |
| Граница доверия | Агент ↔ host adapter ↔ USB/serial ↔ устройство; права host требуют ограничения | Агент/сеть ↔ service/device; аутентификация, транспортная защита и обновление сервиса должны быть спроектированы |
| Риски | Ошибки аргументов/парсинга, чрезмерные права процесса, неоднозначность частичного ответа | Удалённая поверхность атаки, идентификация клиента, секреты, сетевые сбои и обслуживание прошивки |
| Что проверить | Явные allowlist-команды, эффекты, таймауты, идемпотентность, отсутствие автоматических повторов | Модель идентификации и авторизации, защищённый канал, минимальная экспозиция, отказоустойчивость и обновление |

Таблица задаёт вопросы для исследования, а не подтверждённые свойства конкретной реализации.

## Принципы capability-модели

1. **Инвентаризировать возможности, а не обещать универсальное управление.** Для каждой функции записать источник, поддерживаемое устройство/прошивку, входы, выходы, побочные эффекты, ограничения и статус доказательств.
2. **Один семантический API, разные транспорты — возможная гипотеза.** CLI, MCP или другой клиент могут отображать общий каталог именованных операций и структурированных результатов; транспорт сам по себе не должен расширять полномочия. Это кандидат на архитектуру, не принятое решение.
3. **Разделять уровни полномочий.** Наблюдение → ограниченная диагностика → временное управление → постоянное изменение/установка. Каждый следующий уровень требует отдельного описания эффектов, подтверждения и восстановления; read-only ярлык не заменяет проверку побочных эффектов.
4. **По умолчанию запретить произвольное исполнение.** Никаких shell, произвольной записи файлов/памяти, массового чтения хранилища или универсальных GPIO-команд. Расширять каталог только для конкретной проверенной потребности.
5. **Сохранять неопределённость.** Ответы должны различать `PASS`, `FAIL`, `NOT_TESTED`, `INCONCLUSIVE`; таймаут не доказывает, что команда не исполнилась. Не повторять потенциально изменяющую состояние операцию автоматически.
6. **Давать оператору контроль.** Видимые операции, минимум данных, отдельное согласие для изменения/установки, ясная отмена и безопасное поведение при потере связи.

## Этапы исследования

- **A — каталог возможностей:** перечислить ПО, измерения, модули и доступные ресурсы; для каждой записи отметить verified / source-documented / unknown, эффект, риск, зависимости и нужный уровень полномочий.
- **B — контракт:** определить схемы аргументов/результатов, bounds, таймауты, ошибки и правила повтора; проверить, что transport не маскирует неопределённость.
- **C — сравнение архитектур:** оценить обе таблицей выше на одном наборе приоритетных сценариев, угроз, эксплуатации и восстановления; отдельно рассмотреть гибрид.
- **D — прототип:** только после отдельного решения и разрешения, на выбранном пути и ограниченном наборе операций; тесты на host/fake transport прежде реального устройства.
- **E — расширение:** добавлять возможности по одной с анализом эффектов, независимым review, операторским подтверждением и откатом; физические результаты подтверждать наблюдением.

Переход между этапами не является разрешением на COM/serial, сетевой сервис, SD-доступ, установку или запись прошивки. Issue #2 описывает отдельную диагностическую работу и остаётся источником её конкретных ограничений.

## Решения, оставленные открытыми

- Нужен ли удалённый доступ, или достаточно подключённого host?
- Где должны жить учётные данные/идентификация и кто может разрешать операции?
- Какой набор реальных пользовательских сценариев требует доступа к каждой аппаратной возможности?
- Выбирать ли host adapter, device-side service, гибрид или оставить интерфейс локальным?
- Какие постоянные изменения допустимы, как подтверждать их оператором и как восстанавливать устройство?

До ответа на эти вопросы данный план не выбирает MCP-only, сетевое управление или конкретную модель безопасности.
